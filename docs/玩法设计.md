## 一、经济系统

### 1.1 配送费构成

```
配送费 = 基础配送费
       + 距离附加费
       + 天气附加费（雨补）
       × 时段系数
       + 等级加成
       - 平台抽水
```

**基础配送费**：3.50 元

**距离附加费**（分段）：

| 距离 | 附加费 |
|---|---|
| 0 ~ 1.5 km | 0 元 |
| 1.5 ~ 3 km | 1.00 元 |
| 3 ~ 5 km | 2.00 元 |
| 5 ~ 8 km | 3.50 元 |
| > 8 km | 每公里 +0.60 元 |

**时段系数**（模拟真实平台的繁忙度溢价）：

| 时段 | 系数 |
|---|---|
| 早高峰 7:00-9:00 | ×1.10 |
| 午高峰 11:00-13:00 | ×1.15 |
| 晚高峰 17:00-20:00 | ×1.25 |
| 其他 | ×1.00 |

**等级加成**：`等级 × 20 分`（1 级 0 元，6 级 1.00 元）

### 1.2 平台抽水

**控制端可配置，默认 0%**（RMB 1:1 要求）。

| 配置项 | 默认 | 范围 |
|---|---|---|
| 抽水比例 | 0% | 0 ~ 30% |
| 抽水基数 | 配送费 | 只抽配送费，不抽雨补 |
| 抽水时机 | 结算时 | 实时显示到手价 |

```
到手 = 配送费 - 配送费 × 抽水率 - 罚单 - 保险
```

到手不足则扣到 0，但**记录欠款，下一单优先抵扣**。

**「平台歧视性抽水」（可选开关，默认关）**：
```
评分高 / 单量大的骑手 → 抽水上浮（平台认定好压榨）
评分低 / 投诉多的骑手   → 抽水下浮（平台想留住人）
```

这模拟真实平台最脏的地方——**玩家能直接体验"越能干越被抽"**。

### 1.3 时薪

```
时薪 = (今日到手总额 - 今日罚单 - 今日保险) / 在线小时数
```

**在线小时**：上线到下线的累计分钟 ÷ 60。**等餐时间算在线**（这是真实骑手的痛点）。

**这个数字是整个模拟器的核心 KPI，界面必须最大字号显示。**

### 1.4 罚单

| 项目 | 金额 | 触发 |
|---|---|---|
| 等餐超时 | -2.00 元 | 商家出餐超过承诺时限 |
| 送达超时 | -3.00 元 | 超过承诺送达时间 |
| 交通罚款 | -5.00 元 | 超速被拍（档位 1+） |
| 顾客投诉 | -2.00 元 | 可申诉，成功则撤销 |
| 事故医药费 | -20 ~ -200 元 | 交通事故，按严重度 |
| 取消单 | -5.00 元 | 主动取消已接单 |
| 背单全崩 | -2.00 元 | 任一单超时，全部手持单罚 |
| 保险 | -2.00 元/天 | 每日自动扣 |

**所有罚单必须在账单明细里显示原因**，不能只给总数。

### 1.5 惩罚传导链（游戏的灵魂）

```
        超时 / 事故
            ↓
       扣钱 + 掉评分
            ↓
     评分 < 4.6 阈值
            ↓
  可抢订单类型变少（好单派给别人）
            ↓
         单量减少
            ↓
         收入下降
            ↓
    【必须上线才能赚钱】  ← 压力循环形成
```

**这个正反馈是骑手处境的数学表达。设计目标：让玩家体验到"不敢下线"的压迫感。**

## 二、天气系统

### 2.1 天气类型

| 天气 | 速度系数 | 事故率加成 | 雨补 |
|---|---|---|---|
| 晴 | 1.00 | ×1.0 | 0 |
| 多云 | 1.00 | ×1.0 | 0 |
| 阴 | 0.98 | ×1.1 | 0 |
| 雾 | 0.70 | ×2.5 | 1.00 元 |
| 小雨 | 0.85 | ×1.5 | 0.80 元 |
| 中雨 | 0.75 | ×2.2 | 1.50 元 |
| 大雨 | 0.62 | ×3.5 | 2.50 元 |
| 大风 | 0.78 | ×2.0 | 1.20 元 |
| 雪 | 0.55 | ×4.0 | 3.00 元 |
| 暴雨 | 0.45 | ×6.0 | 4.00 元 |

### 2.2 雨补的核心矛盾

**这是最有意思的机制：**

```
雨补 > 0        →  想出门跑
但速度下降 15~55%  →  同样时间跑更少单
且事故率上升 1.5~6 倍  →  可能一场雨亏掉一天
```

**期望值是负的，但玩家不知道具体负多少。** 这就是"要不要在雨天出门"的赌博感。

控制端可以在雨天上浮雨补，制造"平台体面"与"平台剥削"的对比。

### 2.3 天气调度

**按剧本驱动，不是纯随机**：

```jsonc
// data/weather_script.json
{
  "day": "2026-10-06",
  "events": [
    { "at": 390,   "to": "cloudy" },      // 6:30
    { "at": 510,   "to": "light_rain" },  // 8:30
    { "at": 660,   "to": "heavy_rain" },  // 11:00
    { "at": 900,   "to": "light_rain" },  // 15:00
    { "at": 1140,  "to": "clear" }        // 19:00
  ]
}
```

`at` 单位是模拟分钟。**控制端可实时切换天气**，用于测试与演示。

## 三、速度与风险系统

### 3.1 三档速度模式

| 档位 | 名称 | 限速 | 时薪系数 | 事故率 | 评分影响 | 被拍罚款 |
|---|---|---|---|---|---|---|
| 0 | 合规 | 30 km/h | ×1.00 | 0.5% | 无 | 无 |
| 1 | 容忍超速 | 45 km/h | ×1.35 | 4% | -0.01/次 | -5 元 |
| 2 | 解除限速 | 无上限 | ×2.20 | 22% | -0.05/次 | -5 元 |

**控制端开关**：
- `允许超速` — 默认**开启**（玩家可选档位 0~1）
- `允许解限速` — 默认**关闭**（档位 2 是奖励机制，需要主动解锁）

### 3.2 档位 2 的期望值陷阱

**这是设计上的关键点：档位 2 期望值是负的。**

```
单次跑单收益：约 6.5 元
事故率 22%
一次事故：停工 2 小时（损失约 30 元）+ 医药费均 40 元 = 70 元

期望单次成本 = 0.22 × 70 = 15.4 元
期望净额     = 6.5 - 15.4 = -8.9 元
```

**算下来档位 2 是亏的。** 但玩家在赌的时候不知道这个数字，只知道"跑得快钱多"。

**这就是"贪婪的人不一定赢"的设计意图。**

控制端提供 `显示期望值` 开关——**看不看是玩家的选择，但信息是真实的**。

### 3.3 事故判定

```rust
fn accident_probability(speed_ratio: f32, weather: Weather, fatigue: f32) -> f32 {
    let base = 0.005 * weather.accident_multiplier();
    let speed_penalty = (speed_ratio - 1.0).max(0.0) * 0.08;
    let fatigue_penalty = fatigue * 0.02;
    base + speed_penalty + fatigue_penalty
}
```

**事故后果**：
- 停工 1~3 小时（按严重度）
- 医药费 20~200 元
- 评分 -0.05
- 骑手进入 `Injured` 状态，无法接单

### 3.4 超速被拍

```
被拍概率 = 档位系数 × 路段车流量 × 时段系数
档位 1 约 0.8% / 单
档位 2 约 4% / 单
```

**被拍冻结账号 10 分钟**（无法抢单）——**这比罚款更痛**。

### 3.5 疲劳系统

**隐藏属性**，玩家能感觉到"越晚越跑不动"，但看不到数字。

| 行为 | 疲劳变化 |
|---|---|
| 连续在线 1 小时 | +0.08 |
| 每完成 1 单 | +0.01 |
| 下线休息 10 分钟 | -0.15 |
| 每天归零 | → 0 |

**影响**：疲劳同时降低速度上限并提高事故率。

## 四、订单系统

### 4.1 抢单机制

**滑动抢单**（骑手端）：
- 新单从底部滑入，卡片显示商家、距离、时薪预估、剩余时间、顺路提示
- **向上滑 = 抢单，向下滑 = 忽略**
- 抢单窗口 **3 秒**（控制端可调 1~10 秒）
- 窗口内未操作 = 自动放弃

**单卡片信息**：

```
┌────────────────────────────────┐
│ 老王热干面（光谷店）             │
│ 距你 1.2 km · 顺路              │
│ 预计到手 ¥7.20                  │
│ 时薪 ¥38.50 · 剩余 3s           │
│ 备注：不要香菜                   │
└────────────────────────────────┘
   ↑ 向上滑 = 抢单
   ↓ 向下滑 = 忽略
```

**倒计时最后 1 秒卡片变红。**

### 4.2 顺路提示

后台计算 `当前手持单方向` 与 `新单方向` 夹角：

| 夹角 | 提示 | 颜色 |
|---|---|---|
| < 30° | 顺路 | 绿 |
| 30~60° | 一般 | 黄 |
| 60~120° | 逆路 | 橙 |
| > 120° | 完全逆路 | 红 |

### 4.3 指派单

**控制端强制指派**：无视抢单，直接派给某个骑手。

```
指派 → 骑手端弹出确认框 → 3 秒内不确认则自动拒绝
```

**设计意图**：模拟"平台强制派单"。指派单时薪通常低于抢单单——**因为平台知道你会接**。

### 4.4 背单（多任务叠加）

**核心机制：一次出门送多单。**

| 规则 | 值 |
|---|---|
| 最多同时手持 | 3 单（可配 1~5） |
| 绕行超过 | 800 米才值得背 |
| 延误容忍 | 承诺时限 + 5 分钟缓冲 |
| 背单补偿 | 每多背一单 +0.50 ~ 1.20 元 |
| **失败惩罚** | **任一单超时，全部分扣 200 分** |

**核心张力**：

```
背 3 单：收入 +50%，但风险是「一单超时全崩」
```

**最刺激的决策点**：距第 1 单送达还剩 3 分钟，第 3 单背不背？

### 4.5 商家出餐时间

| 时段 | 出餐时间系数 |
|---|---|
| 平峰 | ×1.0 |
| 午高峰 / 晚高峰 | ×2.0 |
| 极高峰（暴雨 + 晚高峰） | ×3.0 |

**商家自身属性**：`avg_prep_min`（5~25 分钟）+ 商家评分影响单量。

## 五、AI 决策系统

### 5.1 AI 骑手策略

```rust
pub struct SimStrategy {
    pub accept_threshold_cents_hour: i64,  // 最低时薪
    pub max_orders_per_day: u32,
    pub accept_extra_tasks: bool,          // 是否背单
    pub speed_mode: SpeedMode,
    pub detour_tolerance_m: u32,
    pub skill: f32,                        // 0~1，影响等餐耐心与找楼效率
}
```

**默认配置**：3~5 个虚拟骑手，阈值在 20~35 元/小时之间波动。高峰期部分虚拟骑手"挑单"（只接高时薪），制造单被抢光的真实感。

**虚拟骑手不会针对真人玩家**（保持公平）。

### 5.2 批量决策

见 [技术设计 §7.2](技术设计.md#72-批量贪心指派)。要点：
- 贪心指派，骑手与订单各只能出现一次
- 复杂度 O(骑手 × 订单 × log n)
- **不用匈牙利算法**（规模小，且贪心结果玩家能看懂）
- 输出分配理由给控制端

### 5.3 LLM 战术大脑（可选，默认关）

见 [技术设计 §7.3](技术设计.md#73-llm-战术大脑可选默认关)。要点：
- **每时段 1 次**，不是每 tick，一天最多 24 次
- LLM 输出 JSON，**代码必须校验**（骑手不重复、订单存在、不在空闲列表的丢弃）
- 超时 3 秒 / 非法 JSON → 放弃本轮，算法兜底
- **不可信任 LLM 的任何措辞**

## 六、任务对话系统

### 6.1 两种模式

| 模式 | 实现 | 优先级 |
|---|---|---|
| **预设任务** | 关键词状态机，JSON 定义 | Phase 6 |
| **LLM 任务** | 结构化判定 + 代码兜底 | Phase 11 |

**任务与订单两条线并行**：任务对话不影响送达流程，骑手可以一边送单一边对话，或在等餐时对话。

**30% 概率订单携带任务。**

### 6.2 预设任务格式

```jsonc
// data/tasks.json
{
  "tasks": [
    {
      "id": "leave_at_door",
      "name": "放门口",
      "steps": [
        { "rider_prompt": "您好，我在小区门口了，放哪个门？",
          "customer_responses": ["放门口吧", "门口有柜子", "放前台"] },
        { "rider_prompt": "好的，密码是多少？",
          "requires_keywords": ["密码", "门禁"],
          "customer_responses": ["密码1234", "没有密码"] },
        { "rider_prompt": "已放在门口，拍照回传。",
          "completion_keywords": ["好了", "放好", "谢谢"],
          "reward_cents": 0, "penalty_cents": 0 }
      ],
      "on_complete": { "rating_delta": 0.0 },
      "on_fail":    { "rating_delta": -0.02 }
    },
    {
      "id": "customer_angry",
      "name": "顾客发火",
      "steps": [
        { "rider_prompt": "抱歉让您久等了，现在已经取到餐了",
          "customer_responses": ["太慢了", "我都等半天了", "还行吧"] }
      ],
      "on_fail": { "rating_delta": -0.05, "penalty_cents": 0 }
    }
  ]
}
```

**完成判定**：命中 `completion_keywords` 任一。

**建议预设 20 个任务**：放门口 / 催单 / 顾客发火 / 找不到路 / 要求重做 / 投诉虚假 / 加急 / 门禁坏了 / 找不到人 / 送错楼层…

### 6.3 LLM 任务（二期）

**核心原则：LLM 只判断，不裁决。**

```
顾客自由输入
      ↓
LLM 输出结构化 JSON
      ↓
代码校验字段合法性并执行
```

```jsonc
// system prompt 要点
{
  "role": "system",
  "content": "你是一个外卖场景的裁决器。只输出 JSON，不要任何解释。
输出格式：{\"task_done\": bool, \"reason\": string, \"rating_delta\": number, \"penalty_cents\": int}
rating_delta 范围 -0.1 到 0.1"
}
```

**必须实现的兜底**：

| 情况 | 处理 |
|---|---|
| API 超时 3 秒 | 按"任务未完成"处理 |
| 返回非法 JSON | 同上 |
| 返回缺字段 | 同上 |
| 服务不可用 | 同上 |

**成本**：假设 20 单有对话，每单 5 轮 = 100 次调用。用 GPT-4o-mini 约 0.1 元。

## 七、界面规格

### 7.1 骑手端 4 Tab

```
┌──────────┬──────────┬──────────┬──────────┐
│  大厅    │ 待取货   │ 待送达   │   账单   │
│  抢单    │  骑手→店 │  店→顾客  │  收入    │
└──────────┴──────────┴──────────┴──────────┘
```

#### 大厅

| 元素 | 说明 |
|---|---|
| 顶部状态条 | 上线状态、当前时薪、今日单量、当前天气 |
| 速度档位切换 | 三档按钮，控制端不允许的档位灰显 |
| 任务对话入口 | 右侧悬浮按钮，有任务时才亮 |
| 单卡片区 | 新单从底部滑入，**滑动抢单** |
| 上下线按钮 | 顶部大按钮，一键切换 |

#### 待取货

| 元素 | 说明 |
|---|---|
| 路线概要 | 距离、预计耗时、天气影响 |
| 商户信息 | 店名、地址、招牌菜 |
| 预计出餐 | 剩余等待时间 |
| 到达按钮 | 到达后切换为"等餐" |
| **背单按钮** | 显示可顺路背的单列表 |

**等餐状态**：显示剩余出餐时间，可"催单"（有概率被拒，扣评分）。

#### 待送达

| 元素 | 说明 |
|---|---|
| 顾客信息 | 称呼、地址、门牌号 |
| 送达方式 | 放门口 / 见面（由任务决定） |
| **手持单列表** | 背了多单在这里全部显示 |
| 剩余时间 | 超时前 5 分钟变红 |
| 交付按钮 | 完成送达 |

**背单展示**：

```
主单：老王热干面 → 1.2km
  └ 顺路单：张记烧烤 → 800m
  └ 顺路单：蜜雪冰城 → 500m
  ⚠ 任一单超时，全部分扣 ¥2.00
```

#### 账单

| 元素 | 说明 |
|---|---|
| **时薪大数字** | 最大字号，核心 KPI |
| 今日到手 | 毛收入 - 罚单 - 保险 |
| 单量 | 完成 / 拒单 / 超时 |
| 明细列表 | 每单可展开 |
| 抽水显示 | `配送费 ¥42.00 - 抽水 ¥8.40 = 到手 ¥33.60` |

**上下线机制**：

```
上线 → 时薪分母开始计时，疲劳开始累积
下线 → 分母停止，疲劳 -0.15（休息 10 分钟），不可抢单
```

**关键：只有上线才能赚钱。** 这是"不敢下线"压迫感的来源。

- 按钮最小 48×48 px
- 单手可操作区域（下半屏）
- 滑动抢单手势灵敏，误触率低
- 竖屏为主，横屏可选

## 八、评分与等级

### 8.1 评分

| 事件 | 变化 |
|---|---|
| 准时送达 | +0.01 |
| 超时 | -0.02 |
| 事故 | -0.05 |
| 顾客好评 | +0.02 |
| 顾客差评 | -0.01 ~ -0.05 |
| 任务完成 | ± 见 `tasks.json` |

**范围 4.0 ~ 5.0，初始 4.8。**

### 8.2 等级

```
等级 = f(累计完成单量)
1 级 0 单      1.0 ×
2 级 50 单     1.04 ×
3 级 150 单    1.08 ×
4 级 400 单    1.12 ×
5 级 1000 单   1.16 ×
6 级 2500 单   1.20 ×
```

**等级加成只影响基础配送费**，不抽成——这是刻意设计的，让"跑得多"确实能多赚。

### 8.3 评分门槛

```
评分 ≥ 4.6 → 可抢普通单
评分 ≥ 4.8 → 可抢优质单（距离远、单价高）
评分 ≥ 4.9 → 可抢急单（加价 30%）
评分 < 4.6 → 只能接低价值单
```

## 九、AI 与算法的边界

| 需求 | 归属 | 原因 |
|---|---|---|
| 抢单决策 | **算法** | 16ms 内完成，要可测 |
| 批量分配 | **算法** | 同上 |
| 金额结算 | **算法** | 绝对不能错 |
| 超时判定 | **算法** | 同上 |
| 天气影响速度 | **算法** | 同上 |
| 疲劳累积 | **算法** | 同上 |
| 任务判定（预设） | **关键词匹配** | 零延迟 |
| 任务判定（LLM） | LLM 判断 + **代码执行** | LLM 只输出 JSON |
| 战术分配（可选） | LLM + **代码校验** | 每时段 1 次 |
| 店名与文案生成 | LLM | 启动时一次性 |
| 天气剧本 | LLM 生成 + **人工审核** | 运行前定稿 |

**判断标准**：

```
需要在 16 毫秒内完成？ → 算法
需要结果可复现？        → 算法
可以偶尔失败降级？      → 可以用 LLM
```

**随机性来源**：固定种子的 ChaCha8 PRNG，**绝不来自 LLM**。

**世界种子做成 UI 输入框**，玩家可输入种子复现任何一局。
