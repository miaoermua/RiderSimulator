## 二、曾经唯一的失败测试（已修，**不是产品缺陷**）

> 2026-10-28：该测试已按下面的根因改成显式 `realtime: false`，`acceptance` 现为
> 11 passed / 0 failed。以下保留当时的定位记录。

`server/tests/acceptance.rs` 的
`speed_multiplier_only_changes_real_time_pacing` 失败：

```
assertion `left == right` failed: 1x 的 tick 间隔不对
  left: 60000
 right: 1000
```

根因：该测试从 `SimConfig::default()` 出发逐个断言倍率档的 tick 间隔，
但 `SimConfig::default()` 的 `realtime` 是 **`true`**（`config.rs:527`），于是
`tick_interval_ms()`（`server/src/sim/config.rs:579-588`）走了实时档分支，
返回 `REALTIME_TICK_MS`（`config.rs:13` = `60_000`）而不是 `1000 / multiplier`。

实现是对的，是测试过期了——实时档功能后加，把 `default()` 的 `realtime` 变成了
`true`，这个更早写的验收测试没跟着调整。对照：同仓库的单元测试
`config.rs:616 tick_interval_scales` 就先做了 `c.realtime = false`，因此通过。

修法（供后续处理，本文不代为改动）：在 `acceptance.rs:277` 的循环之前（紧接
276 行的 `let mut cfg = SimConfig::default();`）加 `cfg.realtime = false;`。
这属于改测试代码，建议独立成一个提交，别和功能改动混在一起。

### 背单容量

- **生效上限** = `min(cfg.backorder.max_held, policy_override.cap_override)`
  （`rider.rs:831`）。覆盖只能往压低，永远不能超过配置里的硬上限；`0` 是合法值，
  语义是「只把手上的送完，不再接新单」。
- 语义是「手上**还没送完**的单量」对上限，不是当天完成量。`check_claimable` 里
  两件事共用 `HeldLimitReached`→`HELD_LIMIT_REACHED`（文案「手持单已达上限」）：
  当日完成量到顶（`reached_daily_cap`）与手持量到顶（`scheduler.rs:164`）。
- 校验点（都在服务端，客户端算的只用于提示）：

  | 业务路径 | 位置 |
  |---|---|
  | 大厅抢单 / 接受指派后抢单（`try_claim` → `check_claimable`） | `scheduler.rs:164` |
  | 控制端派单 / 强制派单（`assign_forced`） | `scheduler.rs:215` |
  | 改派（`reassign`，转给谁就查谁） | `scheduler.rs:348` |
  | 背单加单（`claim_extra`） | `scheduler.rs:469` |
  | 救单（`rescue_nearest` 选人时跳过满载者） | `scheduler.rs:562` |
  | AI 意愿判定（`accepts` / `merge_riders`） | `ai.rs:300` / `ai.rs:330` |
  | AI 一轮批量派单（剩余容量 `per_rider_cap.min(room)`） | `ai.rs:467-473` |

- **强制派单仍受上限约束**（`scheduler.rs:215` 与 `Offer` 走同一条判定）。
  `Forced` 只决定骑手能不能拒，不放大容量；`forced_offline` 的例外是「允许接
  强制单」，也不是「无视上限」。
- **批量不会超容量**：`/api/dispatch` / `/api/reassign` 逐条调用，每条各自校验，
  一条失败不挡后面；AI 一轮里给每个骑手先算 `room = 上限 - 当前持单`，
  再按 `rider_load` 扣掉本轮已派出的条数，所以 `merge.algorithm_max_per_rider`
  调大也不会突破单人上限。
- 客户端展示：快照里每个骑手带 `held_cap`（生效值，见 §六「骑手端」）；
  `held` 是手上订单 id 列表，`held.length / held_cap` 即「手上/上限」。满载
  （含 `held_cap == 0`）时首页顶部出橙色提示条，抽屉与账本显示 `2/3` 这类比值。
  老服务端没下发 `held_cap` 时退回 `config.backorder_max`；**这些只是提示**，
  真正能不能接仍由服务端 `check_claimable` 裁决。

### LLM 决策上下文里的骑手经历

2026-10-28 接入。骑手最近经历（`sim/rider.rs` 的 `RiderEpisode`，上限
`MAX_EPISODES = 5`、按时间从旧到新）现在会随 `BrainRequest` 一起交给模型：

- `RiderSnap.eps`（`llm/protocol.rs:105`）由 `BrainRequest::build` 从
  `Rider::episodes()` 投影而来，五类事件用短码区分：`dl` 送达 / `rj` 拒单 /
  `hd` 扣留 / `fn` 罚款 / `fc` 强制派单（`episode_code`，`protocol.rs:297`）。
  金额字段 `d` 保留正负号、单位**分**；`t` 是**绝对**模拟分钟，不是当天分钟；
  罚款这类不挂单的经历 `o` 为空。
- 没有经历时该骑手连 `eps` 键都不出现（`skip_serializing_if`），不写 `[]` 占位；
  旧载荷缺这个字段也能反序列化（`serde(default)`）。
- 提示词预算仍是 `MAX_PROMPT_BYTES`。经历体量大，裁剪顺序改为
  「备注 → 经历 → 尾部订单 → 尾部骑手 → 硬砍」：`trim_episodes`
  （`protocol.rs:384`）每次从**条数最多**的骑手身上砍掉**最旧**一条，
  保证不会为了塞经历而把整条订单挤出去。
- 决策缓存键 `state_fingerprint`（`protocol.rs:988`）已覆盖每条经历的
  `t` / `k` / `o` / `d` / `n` 全部字段，外加条数；只比条数或只比最后一条都会
  让"换了内容但没换条数"的改动命中旧缓存。缓存键仍是**整批请求一把**，
  所以任一骑手经历变化会让整批失效——安全侧取舍，不是串线。

| `hd` | `Held` | `world.rs:711` | 算法/AI 对某单表态「先观望」，且该骑手本轮首次进入观望窗口 | 0 | 有 |
| `fn` | `Fined` | `economy.rs:197` | 任何一次 `debit` 扣款（超时赔付、取消罚单、保险等） | 真正扣掉的数，取负 | 可能为空（保险没有对应订单） |
| `fc` | `Forced` | `scheduler.rs:248` | 生效派单方式为 `AssignMode::Forced` | 0 | 有 |

`Held` 是「观望/挂起看单」的**决策留痕**，不是「手上有单」；手上有哪些单看
`Rider.held`，两者别混。

**`Forced` 的判定口径**：`assign_forced` 先看骑手是否 `forced_offline`，是则把
传入的 `Offer` 纠正成 `Forced`（`scheduler.rs:198-202`），之后**只看生效值**
决定记不记经历（`scheduler.rs:243-255`）。所以测试
`an_offer_to_a_forced_offline_rider_counts_as_forced` 与「普通 `Offer` 不记
`Forced`」并不冲突：前者传的是 `Offer`，但收件人已被拒单额度逼下线，平台对他
只剩强制派单这一条路；后者是未被强制下线的收件人，`Offer` 保持可拒，不记
`Forced`。判断的是**生效模式**，不是调用方传的字面参数。

**暂未纳入经历的行为**（刻意留白，不擅自映射到现有五种）：
- 取消已接单：通过 `economy::debit` 扣 5 元，会留下一条 `Fined`，不会记 `Refused`；
- 改派（`reassign`）：只写改派日志，不写经历；
- 救单（`rescue_nearest`）：不写经历；
- 拒单额度用尽被自动收下：不写 `Refused`，`RejectLimitReached` 分支提前返回
  （`scheduler.rs:1051-1057`），强制单更不能拒。
