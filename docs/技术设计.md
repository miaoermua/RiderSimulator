## 一、核心架构决策

### 1.1 单一时间权威

**只有后台能推进时间，客户端一律不能自己加时间。**

```
后台：tick 循环，每 tick 推进 1 模拟分钟
  → 通过 WebSocket 广播 tick 事件
  → 客户端按 tick 事件更新显示
```

**原因**：客户端自己推进时间会导致多端时间漂移，"3 秒抢单"这类带时限的决策会算出不同结果，bug 极难查。

**时间倍率**：后台控制。`1x` = 1 现实秒 = 1 模拟分钟。倍率只影响后台的 tick 间隔，不影响模拟逻辑。

### 1.2 状态权威在后台，客户端是纯视图

客户端**不存权威数据**，只缓存用于显示的快照。

```
连接建立 → 后台发 snapshot（世界全量状态）
之后      → 后台发 incremental（增量事件）
断线      → 客户端标脏，重连后重新拉 snapshot
```

**收益**：断线恢复只需一次全量拉取，客户端不需要实现复杂的本地持久化与冲突合并。

### 1.3 抢单是原子的

多个骑手端同时抢同一单，后台必须保证只有一人成功。

```rust
pub fn try_claim(&mut self, order_id: OrderId, rider_id: RiderId)
    -> Result<Assignment, ClaimError>
{
    let order = self.orders.get_mut(order_id).ok_or(ClaimError::NotFound)?;

    if order.status != OrderStatus::Pending {
        return Err(ClaimError::AlreadyClaimed);
    }

    order.status = OrderStatus::Assigned;
    order.assigned_to = Some(rider_id);
    // ...
}
```

单线程 tokio 任务里天然串行，**不需要分布式锁**。

**验收标准**：10 个客户端同时抢 1 单，成功者恰好 1 个。

### 1.4 鉴权过滤在服务端

连接建立时客户端上报身份，后台按身份过滤推送。

**不要靠客户端自觉**。骑手只能收到自己的 `rider_finance`，控制端能收到全部。

**握手三种身份**（`hello` 帧，2026-10-11 起以账号为主）：

| 客户端上报 | 身份 | 说明 |
|---|---|---|
| `rider_name` + `password` | `rider` | **正常路径**。烽火台建的号，见 4.5。 |
| `token` | `rider` / `control` / `spectator` | **开发后门**。`rider:<id>` 绑号、`new:<昵称>` 现场建号、留空观战。 |
| 都不带 | `spectator` | 观战，且受 `RIDER_SIM_ALLOW_CONTROL` 约束才可能变控制端。 |

名字对不上回 `NO_ACCOUNT`，密码不对回 `BAD_CREDENTIALS`，两者都在断开前发一次 `error`。
**服务端不区分「名字不存在」与「密码错」**——免得外人拿它撞名字。客户端要区分时看 `code`。

## 三、模拟内核

### 3.1 固定 tick + 事件队列

```rust
pub struct World {
    pub sim_minute: u32,           // 从当日 0:00 起算
    pub riders: Vec<Rider>,
    pub orders: Vec<Order>,
    pub merchants: Vec<Merchant>,
    pub weather: Weather,
    pub events: VecDeque<SimEvent>,
    pub rng: ChaCha8Rng,          // 固定种子，可复现
}
```

**不要用散装计时器。** 固定 tick + 事件队列让时间加速（`dt` 乘系数）成为唯一的时间控制点，模拟逻辑完全不用改。

### 3.2 状态机

```
Idle ──接单──> ToShop ──到达──> WaitingFood ──出餐──> Delivering ──交付──> Settling
  ↑              │                  │                                     │
  └──────────────┴──────────────────┴─────────────────────────────────────┘
                            ↓
                        Idle（结算完成）
```

| 状态 | 时长来源 | 可否被打断 |
|---|---|---|
| `Idle` | 调度器派单 | 是（接单） |
| `ToShop` | 路线长度 ÷ 速度 | 是（超时） |
| `WaitingFood` | 商家出餐时间，高峰期 ×2~3 | 否 |
| `Delivering` | 路线长度 ÷ 速度 + 找楼时间 | 是（超时） |
| `Settling` | 立即 | 否 |

### 3.3 核心数据结构

```rust
// 金额一律 i64 分
pub struct Order {
    pub id: OrderId,
    pub merchant_id: u32,
    pub customer_lat: f64,          // 6 位小数
    pub customer_lng: f64,
    pub distance_m: u32,            // 整数米
    pub promised_minutes: u32,
    pub created_at: u32,            // 模拟分钟

    // 按「计价规则」算出的单笔明细（起步价/里程/雨补/等级/抽水）
    pub fee: FeeBreakdown,
    // 无人接或被取消后加价重投大厅的次数；重投过但最终被接走的单也有计数
    pub redispatch_count: u32,
    // 重投叠加的调度补贴（分）。全给骑手、不计入抽水基数，
    // 与 fee 分开存，以保证 fee 始终是「按计费规则算出的报价」
    pub surcharge_cents: i64,

    pub status: OrderStatus,
    pub assigned_to: Option<RiderId>,
    pub picked_up_at: Option<u32>,
    pub delivered_at: Option<u32>,

    pub task: Option<TaskId>,
    pub extra_tasks: Vec<ExtraTask>,
}

// 单价系统的落地形态：规则见 SimConfig::fee，明细挂在每一单上
pub struct FeeBreakdown {
    pub base_fee_cents: i64,        // 起步价（含第一档里程）
    pub distance_extra_cents: i64,  // 里程阶梯附加
    pub rain_bonus_cents: i64,
    pub level_bonus_cents: i64,
    pub surge_multiplier: f32,
    pub commission_cents: i64,      // 平台抽水（只抽配送费，不抽雨补）
    pub quoted_fee_cents: i64,      // 报价 = 各项之和
    pub takehome_cents: i64,        // 到手 = 报价 - 抽水
}
// 骑手实际看到的报价 = fee.quoted_fee_cents + surcharge_cents
// 骑手实际到手     = fee.takehome_cents  + surcharge_cents

pub struct Rider {
    pub id: RiderId,
    pub kind: RiderAgent,           // Simulated | Human
    pub name: String,
    pub lat: f64,
    pub lng: f64,
    pub speed_mode: SpeedMode,      // 档位 0/1/2

    pub cash_cents: i64,            // 今日已入账
    pub fines_cents: i64,
    pub insurance_cents: i64,
    pub rating: f32,                // 4.0 ~ 5.0
    pub level: u8,                  // 1 ~ 6
    pub completed: u32,
    pub fatigue: f32,               // 0~1 隐藏属性
    pub online: bool,
    pub online_minutes: u32,
    pub held_orders: Vec<OrderId>,  // 背单
}
```

### 3.4 订单生命周期

```
Pending ──抢单/指派──> Assigned ──到店──> PickedUp ──送达──> Delivered
   │                     │                │                  │
抢单超窗              骑手取消          送达超时            结算
   │                     │                ↓                  ↓
   └──── 加价重投大厅 ◄───┘             Late              Settling
              │
        重投满 3 次仍无人接
              ↓
       Expired（彻底流单）
```

> **不弃单**：抢单超窗、骑手取消都不会让订单凭空消失，而是加价重回大厅
> —— 累加 `redispatch_count`、抬高 `surcharge_cents`（补贴全给骑手），
> 只有重投满 `MAX_REDISPATCH_ATTEMPTS`(3) 次才判 `Expired`。
> `Cancelled` 现为保留枚举值，无路径产生（历史流水与协议仍引用它）。

## 四、跨端契约

**三端共享的唯一事实来源：`packages/protocol.json`**

**先手写定义再写代码**，不要自动生成——生成器在三套语言里行为不一致。

### 4.1 契约铁律

| 项 | 约定 | 错误示例 |
|---|---|---|
| 时间戳 | 整数，**模拟分钟**（当日 0:00 起算） | `1699999999` |
| 金额 | 整数，**单位「分」** | `35.5` |
| 坐标 | **独立字段 `lat` / `lng`**，禁止数组 | `[116.3, 30.5]` |
| 坐标精度 | 6 位小数 | 12 位 |
| 距离 | 整数，**米** | `1.2` |
| 状态枚举 | 字符串，不用数字 | `status: 1` |
| 缺失字段 | 必须是 `null`，不能省略 | 字段干脆不传 |
| 错误码 | 固定字符串枚举 | 中文原文 |

> 坐标是三端最容易出错的地方。高德用 `[lng, lat]`，GeoJSON 用 `[lat, lng]`。**用独立字段从根上避免搞错。**

### 4.2 消息信封

```jsonc
// 请求
{ "type": "req", "id": "r_001", "action": "claim_order", "payload": { "order_id": 42 } }

// 成功响应
{ "type": "res", "id": "r_001", "ok": true, "payload": { "assignment_id": 7 } }

// 错误响应
{ "type": "res", "id": "r_001", "ok": false, "error": "ALREADY_CLAIMED", "message": "订单已被抢走" }

// 事件
{ "type": "evt", "name": "order_broadcast", "payload": { /* ... */ } }
```

**`error` 用固定字符串枚举**，中文可能改，枚举不能改。

### 4.3 动作清单

| action | 发送方 | 说明 |
|---|---|---|
| `hello` | 客户端 → 后台 | 上报身份：`rider_name`+`password`（账号）、`token`（后门）、或都不带（观战）。见 1.4 / 4.5 |
| `change_password` | 骑手 → 后台 | 改自己的密码，`old_password` 必须对。已发出的二维码里的密码就此作废 |
| `claim_order` | 骑手 → 后台 | 抢单 |
| `claim_extra` | 骑手 → 后台 | 背单 |
| `reject_order` | 骑手 → 后台 | 拒绝一张**待确认的指派单**（吃拒单额度、不罚钱），或退回一张**已接下的单**（罚钱、不吃额度）。服务端靠 `assign_pending` 标记区分 |
| `accept_assign` | 骑手 → 后台 | 确认收下指派单，摘掉待确认标记。幂等。**不接受就退单会被当成拒指派、白吃一次额度**，所以客户端必须发 |
| `arrive_shop` | 骑手 → 后台 | 到达商家 |
| `arrive_customer` | 骑手 → 后台 | 到达顾客 |
| `deliver` | 骑手 → 后台 | 完成交付 |
| `online` / `offline` | 骑手 → 后台 | 上下线 |
| `assign_order` | 控制端 → 后台 | 指派单 |
| `create_order` | 控制端 → 后台 | 临时插一张订单：商家名 / 两端坐标 / 金额可填。坐标按**当前下发坐标系**传，换算在服务端入口做；金额给了就直接当最终报价（夹在 1~2000 元） |
| `reset_rider_wallet` | 控制端 → 后台 | 清空某个骑手的钱包（纯测试辅助，控制台负责二次确认） |
| `set_weather` | 控制端 → 后台 | 切换天气 |
| `set_config` | 控制端 → 后台 | 改抽水、速度限制等（含 `max_rejects_per_day`，`0` = 不限） |
| `force_state` | 控制端 → 后台 | 强制改状态 |
| `set_speed` | 控制端 → 后台 | 改模拟倍率 |

### 4.4 事件清单

| 事件 | 推送给 | 说明 |
|---|---|---|
| `snapshot` | 全体 | 连接后首次，全量状态 |
| `tick` | 全体 | 模拟时间推进 |
| `order_broadcast` | 全体骑手 | 新订单产生（含倒计时） |
| `order_claimed` | 全体 | 谁抢到了哪单 |
| `rider_state_changed` | 控制端 | 骑手状态变化 |
| `rider_finance` | 骑手本人 | 收入变动 |
| `weather_changed` | 全体 | 天气切换 |
| `fine_issued` | 骑手本人 + 控制端 | 罚单 |
| `assign_rejected` | 骑手本人 + 控制端 | 拒掉了一张待确认的指派单，带 `used` / `limit`（`limit = 0` 表示不限） |
| `ai_decision` | 控制端 | AI 分配结果与理由 |
| `activity_reward` | 骑手本人 + 控制端 | 平台活动达成，奖金已自动入账 |
| `notice_changed` | 全体 | 首页通知被改 / 清空。`notice = null` 表示收起条子 |
| `day_closed` | 全体 | 日结完成 |

**骑手只能收到自己的 `rider_finance`**，看不到别人收入。过滤在服务端做。

**首页通知只有一条**：烽火台写标题 + 正文，可选关联一个平台活动；改了就覆盖，
没有列表也没有历史。手机首页原来「在线 / 今日收入」的条子就是它——不写就不
显示，点开看全文，关联了活动还会附上「我的进度」。所以快照里带 `notice`，
变更走 `notice_changed`，而不是让客户端轮询。

### 4.5 骑手接入：二维码即登录凭证

**要解决的问题**：骑手拿到手机，怎么不用手输一长串服务器地址就能连上来。

**做法**：烽火台（`server/console`）给每个账号生成一张二维码，内容是

```
ridersim://login?host=<手机可达地址>&port=<端口>&name=<骑手名>&password=<明文密码>
```

权威实现在 `server/src/net/join.rs`（`JoinInfo::login_uri`），客户端解析在
`client/lib/login_link.dart`，契约在 `packages/protocol.json` 的 `login_uri`。
**三处必须同时改**。

**为什么把明文密码放进去**（2026-10-11 定）：

- 扫码即登录，不依赖服务端存会话、不依赖票据过期时间——是最少的状态。
- 代价很实在：这张码能截图、能打印、**发出去收不回来**。
- 唯一的作废手段是重置该骑手密码（密码一变，旧码当场失效）。所以「重置密码」
  在烽火台上必须是一等公民，且要提示管理员「旧二维码会失效」。

**host 必须是手机可达的地址**。`127.0.0.1` 到了手机上指的是手机自己——这是最容易
踩的坑。服务端按「显式配置 `RIDER_SIM_PUBLIC_URL` / `RIDER_SIM_PUBLIC_ADDR` > 监听地址 >
探测局域网 IP > 回环兜底」排序给出候选，并过滤掉 fake-ip 段（`198.18.0.0/15`，代理软件常占）。

两个环境变量的分工（2026-10-17 加）：

- `RIDER_SIM_PUBLIC_ADDR=game.example.com[:9000]`：只换主机，协议固定 `ws://`、
  路径固定 `/ws`。
- `RIDER_SIM_PUBLIC_URL=wss://game.example.com/rider/ws`：**整条地址原样使用**，
  协议、端口、路径都不再补。反代在 https 后面、或服务挂在子路径下时只能用它。
  二维码里会多带一个 `url=` 字段，客户端优先取它；老客户端忽略它、退回
  `host` / `port`，扫了仍能用（只是连不到反代后面）。
- 两个都配时以 `RIDER_SIM_PUBLIC_URL` 为准。

**账号表**（`account`）：`name` 主键 + `password_hash` + `created_at` / `updated_at`。
**只存 Argon2 哈希，不存明文**——所以明文只在两个地方出现：建号/改密的 HTTP 响应、
以及那张二维码。

| 接口 | 说明 |
|---|---|
| `GET /api/accounts` | 名单 + 可达地址。**不含密码** |
| `POST /api/accounts` | 建号。重名回 409 且**不覆盖原密码**，否则已发出的码会莫名失效 |
| `POST /api/accounts/{name}/password` | 改 / 重置密码 |
| `DELETE /api/accounts/{name}` | 删号 |

这些是**管理动作，走 HTTP 不走 WS**：不进 16ms 的帧流，且明文密码只出现在
那一份响应里。鉴权与 `/ws` 同一套令牌。

骑手在几个商圈里跑，路线重复率极高。缓存 2000 条能把日请求压到 100 次内。

**③ 必须解析 `status` 字段**


常见 `infocode`：`10001` Key 非法、`10002` 服务未开通、`10003` Referer 校验失败、`10005` 配额超限。

**④ 超限静默降级**


**游戏不能因为 API 挂了卡住。**

## 六、AB 点圆滑轨迹

### 6.1 轨迹生成

```rust
pub fn build_trajectory(
    polyline: &[LatLng],
    speed_mps: f32,
    seed: u64,
) -> Vec<Waypoint> {
    let total = polyline_len(polyline);
    let total_time = total / speed_mps;

    // 沿折线按弧长等距采样
    let samples = sample_by_distance(polyline, total_time);

    // Catmull-Rom 插值让曲线圆滑
    catmull_rom(samples, tension: 0.5)
}
```

**不要直线插值**——真实骑行要跟路网。

### 6.2 速度曲线

```
速度 = ease_in_out(t) × 目标速度 × 天气系数
起步 2 秒加速到 80%
匀速段
抵达前 3 秒减速到 0
```

**雨天减速**：目标速度 × 天气速度系数。

**红灯停顿**：随机在路口插入 5~20 秒停顿。

### 6.3 降级轨迹

| 情况 | 轨迹 |
|---|---|
| 高德正常 | 真实路网 polyline |
| 超配额 / 断网 / 报错 | 直线 + 随机偏移（每 50m 偏 3~8m）+ 小幅抖动 |

**降级轨迹必须看起来像在走。** 完美直线会让玩家一眼看出是假的。

## 七、AI 批量决策

### 7.1 单骑手打分

```rust
score = 时薪 × 0.4
      + 顺路度 × 0.3
      + 距离偏好 × 0.2
      + 商家评分 × 0.1
      - 背单风险 × 0.25
```

### 7.2 批量贪心指派

```rust
pub fn batch_decide(
    &mut self,
    new_orders: &[OrderId],
    idle_riders: &[RiderId],
) -> Vec<Assignment> {
    // 1. 构造所有 (骑手, 订单) 候选对
    let mut candidates: Vec<Candidate> = new_orders.iter()
        .flat_map(|oid| idle_riders.iter()
            .map(|rid| self.evaluate(*rid, *oid)))
        .filter(|c| c.score > c.threshold)
        .collect();

    // 2. 按分数降序
    candidates.sort_by(|a, b| b.score.cmp(&a.score));

    // 3. 贪心分配，骑手和订单都只能出现一次
    let mut used_riders = HashSet::new();
    let mut used_orders = HashSet::new();
    let mut result = Vec::new();

    for c in candidates {
        if used_riders.contains(&c.rider) || used_orders.contains(&c.order) {
            continue;
        }
        used_riders.insert(c.rider);
        used_orders.insert(c.order);
        result.push(Assignment::from(c));
    }
    result
}
```

**复杂度** O(骑手数 × 订单数 × log n)，10 骑手 × 5 单完全无压力。

**不用匈牙利算法**——10×5 规模最优解没意义，而且贪心的分配结果玩家能看懂为什么。

### 7.3 LLM 战术大脑（可选，默认关）

每时段调用一次，**不是每 tick**。

```jsonc
{
  "assignments": [
    { "rider_id": "r1", "order_id": 42, "reason": "顺路且时薪高" },
    { "rider_id": "r3", "order_id": 43, "reason": "距离近" }
  ]
}
```

**代码必须做的校验（不信任任何输出）**：

```rust
fn validate_llm_assign(parsed: &LlmResponse, idle: &[RiderId], orders: &[OrderId])
    -> Vec<Assignment>
{
    let mut riders = HashSet::new();
    let mut order_ids = HashSet::new();
    let mut out = Vec::new();

    for a in &parsed.assignments {
        if !idle.contains(&a.rider_id) { continue; }
        if !orders.contains(&a.order_id) { continue; }
        if !riders.insert(a.rider_id) { continue; }      // 重复骑手 → 丢弃
        if !order_ids.insert(a.order_id) { continue; }  // 重复订单 → 丢弃
        out.push(*a);
    }
    out
}
```

**兜底**：超时 3 秒 / 非法 JSON → 放弃本轮，用算法决策兜底。一天最多 24 次调用。

## 八、模拟内核的零 IO 约束

`server/src/sim/` **禁止任何 IO**：

- ❌ 不打日志
- ❌ 不读文件
- ❌ 不发网络请求
- ✅ 纯函数与纯状态变换

**理由**：这样才能写"跑 10 万 tick 验证不 panic、金额不为负"这种测试。IO 会让测试变慢且不确定。

需要 IO 的部分（读商户、调用高德、写数据库）放在 `sim/` 之外，通过参数传入。

```rust
// 好的写法：依赖通过参数传入
pub fn tick(world: &mut World) -> Vec<SimEvent> { /* ... */ }

// 好的写法：距离计算在这里，但 haversine 本身是纯函数
pub fn travel_minutes(distance_m: u32, speed_mps: f32, weather: Weather) -> u32 {
    let effective_speed = speed_mps * weather.speed_factor;
    (distance_m as f32 / effective_speed / 60.0).ceil() as u32
}
```

## 九、验收标准

| 项 | 标准 |
|---|---|
| **时间一致性** | 多客户端看到的模拟时间误差 < 1 tick |
